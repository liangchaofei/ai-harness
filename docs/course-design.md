# 新版课程设计：从零建设 Agent Runtime 与 Harness

状态：供审阅的设计草案。不是新教程正文，不替换现有课程，不授权清理仓库或重写学习源码。

## 1．整门课程的目标

面向具备 TypeScript、Node.js、前端与一般后端开发经验，但尚未系统学习 Agent 的工程师。

最终目标是：理解并能够独立设计、实现、调试、扩展和评估 Agent 系统；亲手建设一个职责清楚、可独立安装使用的 TypeScript Agent Runtime/Harness 底座，并让命令行 Coding Agent 与桌面 Coding Agent 通过公开接口使用它。

“最小 Agent”只是第一阶段的教学起点。它既不是课程终点，也不是整个项目的能力定位。课程不能在一个模型加工具的循环跑通后，就宣称完成了 Agent 技术学习。

岗位 JD 用来约束能力覆盖，Pi 用来提供局部源码与设计对照。课程不照抄 Pi 目录，不追逐它的全部功能，也不把某个参考框架当作全部岗位技术的定义。课程成果应能形成可解释的工程作品；岗位中的学历、年限、团队协作与生产规模经验不由教程授予。

## 2．采用的学习路线及替代方案

考虑过三种路径：

| 路径 | 优点 | 与当前目标的取舍 |
|---|---|---|
| 直接逐目录阅读 Pi | 接触真实工程，实现完整 | 对 Agent 初学者同时暴露太多职责，很难判断代码存在的原因 |
| 使用成熟框架做多个应用 | 较快获得应用结果 | 可以作为后续对照，但不足以支撑亲手建设 Runtime 的目标 |
| 从零建设同一底座，阶段性对照 Pi | 能理解每项机制的来源，并逐步形成实际系统 | 需要维护路线、验证边界与合理节奏；本课程采用 |

采用第三种路线。作者在设计每章前先研究Pi对应源码，提炼职责与可核查依据；读者先理解并实现本阶段机制，再阅读对应局部，比较职责与边界；适时增加框架使用对照，但不把主要实现委托给一个隐藏底层行为的 Agent 框架。

## 3．课程中的几个名称

这些术语在行业中存在不同用法，本课程按职责约定使用，不建立人为的严格包含关系。

| 名称 | 本课程指什么 | 不应混淆 |
|---|---|---|
| 模型接入 | 把请求、响应及流式事件连接到模型服务 | 模型客户端本身不等于 Agent |
| Agent 行为 | 根据目标与可见信息选择动作，利用环境反馈继续推进任务 | 预先写好的固定动作序列不能证明自主决策能力 |
| Runtime | 承载 Agent 运行的执行循环、工具执行、状态、生命周期与运行控制 | 不等于操作系统，也不要求从零实现容器或数据库 |
| Harness | 围绕运行提供接入、上下文、安全、持久化、观察与评估等工程设施 | 不能用模块数量证明可靠性；具体部署仍需要系统工程 |
| Coding Agent 应用 | 提供代码任务、工作环境、工具、接受条件与交互 | 不把代码编辑和 Git 业务写进通用执行内核 |
| 示例与验收材料 | 用于练习和检查的代码仓库、输入与预期结果 | 不是核心框架的一部分，也不是 Agent 自主成功的证明 |

Runtime 能力从早期开始建设，Harness 随可靠性与扩展需求逐步形成，不能简单按“先写完 Agent，再开始 Runtime”切成两套项目。

## 4．最终工程产物与早期边界

最终交付应包含：

1. 可打包、可从独立消费项目安装的框架包，提供明确的运行接口、类型、事件与扩展契约。
2. 一套支持真实代码任务的工具接入与工作环境，保持与通用核心分离。
3. 使用框架包的命令行 Coding Agent，作为中期可用入口及后续回归入口。
4. 使用同一框架包的桌面 Coding Agent，支持会话、运行过程、交互与结果审阅。
5. 用于复现任务、注入故障、评估质量和比较回归的材料与记录。
6. 可独立跟做的教程、必要配图、局部源码对照与开发者接入说明。

项目采用 **TypeScript monorepo＋workspace分包**。正式分离通用库、能力接入与应用，实际通过包的公开入口消费；不使用跨包相对路径直接导入内部源码。

目标结构如下，包名为工作名称，目录按阶段出现，不在第一篇填满空骨架：

```text
packages/
  model/              模型调用契约、提供商适配与流式事件归一
  runtime/            Agent循环、工具执行、运行状态与生命周期
  harness/            会话、上下文、持久化、策略与扩展的组合入口
  coding-tools/       代码工作区、读写搜索与执行验证能力
apps/
  coding-cli/         组装框架与代码工具，提供命令行交互
  desktop/            桌面界面及本地运行进程接入
examples/             通过公开包入口演示和迁移通用能力
fixtures/             独立、可重置的任务代码与材料
evals/               独立任务集、验收与运行比较
site/                 教程与候选快照
docs/                 设计、内部验证与学习记录
```

选择具体workspace工具、构建工具和桌面技术时，由作者给出依据并确定；不让工具选型占据Agent教学主线。

分包按下列节奏落实：

- 第一阶段建立`model`与`runtime`的职责和真实消费关系：先只支持一个实际模型提供商，随后形成循环；不先建全提供商注册系统。
- 第一阶段03先建立`coding-tools`最小只读工具，首次实际能力就与通用内核分离；第三阶段扩展工作区、修改、执行验证并增加`coding-cli`。工具通过契约传入，不由runtime导入coding-tools。
- 第四至六阶段随着上下文、会话与策略的真实实现建立`harness`组合层；它依赖runtime，不把全部设施持续塞进循环文件，也不为了目录完整提前创建空框架。
- 第八阶段增加桌面应用，收敛SDK兼容性。内部包都要有明确exports、类型和构建产物；阶段节点用打包产物在仓库外验证接入，避免只在monorepo里“看起来能用”。

依赖方向：应用按需依赖harness、coding-tools或runtime；harness依赖runtime，runtime通过模型契约接入model。通用库不反向依赖应用、示例或任务材料。包内基础函数优先在包内复用，不先增加万能utils包。实际图在各阶段只展示已实现部分，未来部分明确标注。

核心不依赖 examples、fixtures、CLI 或桌面 UI。应用负责配置任务、工具、环境、凭据与任务接受规则，核心负责按契约执行并暴露状态与事件。任务接受检查以可选接入点提供，不把一种答案 JSON 或某个业务验收格式规定为所有任务的协议。

普通数据校验可以在所属包内部共用；只有真实跨包复用才考虑独立公共包。避免把不明归属的逻辑全部放进 shared，也不因为被 Agent 使用就全部放进 agent 目录。

第一阶段建立实际本地包入口和消费关系，之后验证构建产物与外部安装。发布 npm 是后续可选操作，需要另行授权；能够独立消费与公开发布是两件事。

### 面向企业使用的工程验收目标

最终目标不是仅在固定材料上跑通的demo。下列要求是主课程的工程验收项，不是写完案例后可随意省略的装饰：

| 方向 | 最终需提供的行为或证据 |
|---|---|
| 真实复用 | 不同任务和CLI/桌面使用同一底座；核心无需因业务材料改变而改循环 |
| 生命周期 | 运行成功、失败、取消、超时、待批准等状态有明确归属与退出处理；不同会话互不污染 |
| 可靠恢复 | 可复现中断、恢复和重复请求；区分未执行、已执行及结果不确定，不承诺任意外部副作用恰好执行一次 |
| 执行控制 | 工具参数、权限与资源限制在执行前检查；审批与具体动作关联；受限目录和真正沙箱区别明确 |
| 信息管理 | 记录与发送分离；摘要/检索可追溯来源，比较策略对任务质量、成本与延迟的影响 |
| 可诊断性 | 关联run/session/model/tool记录；能从故障定位首次偏离；敏感信息不直接进入默认日志 |
| 任务质量 | 多个独立任务与失败材料，有可复现验收和回归；不以模型自行声称完成作唯一标准 |
| 包与SDK | 公开入口、类型、版本与兼容性说明，外部安装消费，接入文档和CI检查 |
| 应用接入 | CLI与桌面复用运行能力，UI与执行进程边界清楚，凭据由合适的本地进程管理 |

这些要求需要随阶段逐步实现和验证。早期可以小，后期必须有对应工程能力；不能把“教学简化”作为永久跳过的理由。每阶段验收记录列出已实现、实验策略、已知缺口与后续处理阶段。企业可用性最终仍需要具体部署环境、业务风险与实际负载验证，课程不把未验证能力写成已经具备。

## 5．八个阶段：每阶段都扩大同一系统的能力

下表中的阶段成果用于课程建设和验收，不自动表示学习者已经掌握。各阶段具体章节在进入该阶段前细化。

第二阶段已确定加入多提供商适配：model包实际接入第二家服务，应用选择接入，复用同一Runtime循环；04先建立模型调用函数注入边界。实施范围与验收见[第二阶段规划](stage-02-plan.md)，当前尚未实现。

| 阶段 | 核心问题 | 主要内容 | 可运行成果与阶段验收 |
|---|---|---|---|
| 一：基础原理与首个可运行内核 | 模型怎样从回答问题变成选择动作？ | 必要模型常识、消息与上下文窗口、工具协议、执行、反馈、循环、停止；最小本地包边界 | 示例通过核心包运行，自主选工具完成小任务；读者能追踪一次请求到下一轮，并换工具而不改循环 |
| 二：可接入、可观察、可控制的内核 | 任务换了、用户取消了、工具失败了，谁负责？ | 模型适配边界、工具契约、参数验证、已知与未知失败、运行状态、事件、基础流式输出、取消、时限与预算 | 两个不同任务复用内核；应用能展示过程和停止运行；分别复现工具失败、模型失败与取消，状态不混淆 |
| 三：实际代码任务与交付 | 怎样从调查进入修改、验证与反馈调整？ | 代码工具与工作区、修改及验证、任务约束、失败后的动作变化、完成接受；按任务需要比较直接循环与显式计划 | 初步 Coding CLI 在可重置工作区完成有限代码任务；看实际差异和验证结果，换任务后仍能使用同一底座 |
| 四：长任务的信息管理 | 信息太多、旧线索消失，下一步怎样仍有依据？ | 消息历史、运行状态与模型输入分离，token预算，选择/裁剪/摘要，来源追溯，检索与RAG，短期与长期记忆 | 在可比长任务上比较策略；说明保留/丢失了什么，观察完成质量与代价；跨会话记忆不会冒充本次已验证事实 |
| 五：可靠执行与恢复 | 运行中断以后，凭什么继续，哪些动作不能重做？ | 会话与状态持久化、检查点、恢复、错误分类、受限重试、退避、幂等、副作用、预算和资源清理 | 注入中断后恢复；记录动作是否已执行；解释不确定副作用，避免盲目重试、伪造成功与无限循环 |
| 六：扩展、安全与人工介入 | 怎样接入更多能力，并控制执行权限？ | 工具扩展、MCP、Skill、人工澄清/批准、暂停继续、权限策略、执行隔离、审计边界 | 接入外部能力无需修改循环；拒绝未授权动作；批准绑定具体操作，不能用目录限制冒充系统沙箱 |
| 七：评估、调试与任务编排 | 怎样知道改进有效，什么时候需要多个Agent？ | 结构化追踪、归因、记录回放、离线任务集与回归，质量/成本/延迟；随后学习委派、汇合、取消、并发/深度/额度限制 | 能复现一次失败并定位首次偏离；用相同任务比较改动；多Agent产物、状态与权限边界明确，并比较单Agent基线 |
| 八：框架收敛与桌面Coding Agent | 怎样让独立应用可靠使用自己的框架？ | 包接口与版本、外部安装验证、接入文档、桌面进程通信、会话展示、流式事件、人工介入、凭据与生命周期 | CLI与桌面通过同一公开接口消费框架；渲染进程不直接持有执行能力或密钥；跑通真实任务与中断/批准路径 |

### 阶段的前置关系与交织

- 阶段一完成的是入门闭环，不是最终目标。之后始终建设同一个系统，不复制八套独立示例。
- 基本任务验证从第一阶段出现；阶段七把它建设成系统评估能力，不是到那里才判断结果好坏。
- 简单事件早期出现，后续再完善关联标识、追踪、记录与回放。“回放记录”与“重新执行工具”必须区别。
- 第三阶段涉及修改与执行之前就设置有限环境、可重置材料和必要权限边界。阶段六再系统学习审批、策略与真实隔离；不先开放任意终端再等后面补安全。
- 第五阶段的恢复会为第六阶段持久化等待批准提供基础；进程恢复不等于所有I/O都可精确恢复。
- 阶段七先建立单Agent质量与成本基线，再引入多Agent，防止用更多模型调用代替机制理解。
- 计划是按任务需要引入的机制，不强迫每个简单任务先创建和更新计划，也不声称显式计划必然更好。
- 第一阶段就有包消费边界，第八阶段才系统收敛兼容性与应用接入，不把独立包目标一直推到结尾。

## 6．岗位能力覆盖与生产专题

三份JD的可见要求及来源记录保存在现有 `docs/jd-learning-map.md`。新设计采用下列覆盖，不继承旧章节“已掌握”的判断。

| JD技术方向 | 主建设阶段 | 具体学习或实现依据 |
|---|---|---|
| Agent Loop、ReAct、理解/执行/反馈/重规划 | 一至三，贯穿后续 | 区分工具请求与执行、环境反馈与下一步、计划与任务完成；不要求输出隐含思维链 |
| 状态、持久化、断点恢复 | 二、五 | 状态归属、检查点、副作用与恢复一致性 |
| Context/Memory、压缩与关键信息保持 | 四 | 输入组装、来源、失效与策略质量对照 |
| Tool/Skill、参数、安全、沙箱 | 二、三、六 | 契约、本地验证、外部协议、扩展、权限和隔离 |
| Human-in-the-loop | 六，八接入界面 | 澄清、批准、暂停、恢复及操作绑定 |
| Tracing、归因、回放、调试 | 二起步、五记录、七系统化 | 关联调用与状态，定位偏差，控制重新执行 |
| 离线评估、回归、完成度、成本延迟 | 各阶段验证，七系统化 | 确定性验收、人工语义评审与受限模型评分分别使用，不承诺任意任务确定正确 |
| Orchestrator、子Agent、并发与嵌套限流 | 七 | 委派契约、状态汇合、失败传播与共享预算 |
| SDK/API、模型适配、插件规范与文档 | 一至二建立，六扩展，八收敛 | 真实消费包接口，不复制内部源码接入 |
| RSI/自进化与问题聚类 | 七之后的深化专题 | 先根据失败分类提出改动，再做独立回归；不把自动改提示词当作能力已经实现 |
| 账户权限、数据库、对象存储、队列、灰度与高可用 | 核心后生产接入专题 | 讨论并实现受限接入，区分身份与授权、单机与分布式、框架与部署责任 |

生产接入不是可以忽略的JD内容，但它与本地框架主线分层。核心八阶段后单独展开后端服务化、身份/租户、存储和队列接入、部署及运行观测，作为AI全栈方向的延伸。工作年限、跨团队交付与真实高可用仍需实际工程经历。

不把“从零”理解为重写HTTP客户端、JSON Schema库、数据库、容器运行时或桌面平台。与教学主线无关且已有可靠方案的基础设施可以直接使用，并说明由谁提供、我们接入什么、没有实现什么。

## 7．章节怎样写

每篇先形成一个有意义的能力增量，再拆成容易理解的小步骤。章节不是按函数、文件或一次报错机械切分。

一篇正常章节的阅读顺序：

1. 具体问题与前后行为：本章结束后系统能多做什么。
2. 系统位置：在累计职责图高亮本章，并用少量文字解释前置关系。
3. 一次具体过程：目标、请求参数、实际执行、返回数据、状态、下一轮和交付条件。
4. 机制推导：为什么需要这个职责，现有实现哪里不足，还有什么较简单的办法。
5. 分步实现：明确文件及位置，连续可复制的逻辑块；中文意图注释；代码后紧邻关键解释。
6. 尽早运行一个完整阶段：预测值、断点位置、实际日志或状态，不让读者读完几百行才第一次运行。
7. 正常、失败与迁移：保留可逆实验，观察下一步如何变化及状态是否正确。
8. 必要的Pi局部对照：固定版本、具体文件与代码范围、同异点；未涉及的职责明确留白。
9. 同源完整文件、验收记录与Git保存命令：中文提交说明、带引号heredoc和对应push，由学习者执行。

完整文件用于核对，不代替教学。多步处理的新模块配整体图；数据与调用难串联时再加具体轨迹图，不机械每章三图。图必须与本章实际行为一致并渲染检查。

公开正文只描述读者从上一章到本章的实现路径。作者草稿、聊天修订、中间文件名和未交付版本不进入正文。不能让读者移动一个在学习起点不存在的文件；迁移说明只针对实际已教过的版本。

配套业务与环境准备提供完整代码、明确路径与接线，不隐去必要材料，也不默认占用主要讲解。新增代码前查已有能力与依赖，发现实际重复及时提炼；任务专属规则不为了消重强塞进公共模块。

本轮设计不改变“不安排单测教学”的现有约定。先用类型检查、运行、断点、故障与迁移建立理解；作者可在临时目录做更完整行为检查。未来若要系统教授自动化测试，再单独明确范围。

## 8．怎样约束偏航

### 章节开写检查

作者在内部规划回答：新增行为是什么、属于哪层、为什么现在需要、复用什么、怎样验证、哪些配套不展开、对应哪个JD能力与阶段成果。正文开头也用简短明确的文字展示“当前阶段、本章新增行为、服务的阶段成果”，让学习者无需查看内部记录就能判断是否偏航。

如果只得到“多一个工具/字段/文件”，且没有可观察能力增长，不据此单独开章。基础概念首次介绍可用小例子，但必须接回阶段成果，不能用此例外无限延续演示。

### 阶段收尾检查

运行新的任务或材料，检查整个累计系统：核心是否依赖案例、入口是否绕过接口、以前的机制能否协作、失败是否可解释、代价是否有记录。对具体不足安排下一阶段练习，不因单次报错自动改变总路线。

### 先通过实际样章校准教学

大纲不能证明实际教学体验。新版第一篇应作为正式课程样章，按最终写作标准交付：具体场景、整体位置、必要图解、分步解释、连续代码、运行观察与完整核对。读者按样章阅读和实现后反馈，再修正后续讲解节奏；不预先批量生成几十篇。样章仍是累计项目第一步，不另造一套体验demo，也不拿项目初始化与目录配置充当整篇核心内容。

若一篇开始主要讲辅助函数、目录清理或业务准备，作者应先重新检查主能力与范围；不能不断追加解释，让学习者承担发现主线偏移的责任。

### 变更方式

普通命名、少量函数提炼和示例选择由作者处理，不要求学习者反复审批。改变阶段目标、核心职责、重要技术选型或学习工作量时，说明原因并讨论。小修订合并回正文，不能无限追加“补充说明”。

内容已提供、作者验证通过、学习者独立实现、独立迁移和延迟复用分别记录。不以“继续”、提交、工具成功或固定响应轨迹判断掌握，也不按章节数量声称完成JD技术百分比。

## 9．规划粒度与第一阶段的细化方向

先稳定总路线；进入每阶段前写阶段大纲，再逐篇完成正文与候选。现在不固定总篇数，也不提前冻结后续API。章节长度以读者能跟做一个增量为准，不以故意拆细增加篇数。

第一阶段当前细化为以下连续单元，具体后续接口仍在实现前核对：

1. 从包入口发起一次模型调用：把最终系统位置与实际请求合在样章，讲清消息、服务响应和文本结果。
2. 模型提出工具请求：让输出表达需要的动作，区分请求和实际执行。
3. 本地执行并反馈：建立Runtime起点，关联工具请求与真实结果，交回下一次调用。
4. 自动继续与停止：由响应决定继续动作，程序约束轮次和退出，形成循环。
5. 换任务检验运行内核：通过公开包入口替换任务与工具，检验状态、材料和核心职责。

不单独用一整篇介绍目录或网站初始化；工程配置完整提供但服务于当前行为。01已提供样章和候选，02–05仍为阶段规划，不据候选存在推断学习源码已实现。

这只是第一阶段的建设顺序。后续还有七个核心阶段和生产专题；首个循环不承担持久化、完整权限或通用任务编排承诺。

## 10．Pi与公开资料的使用

- [Hugging Face Agents Course](https://huggingface.co/learn/agents-course/en/unit0/introduction)：参考基础、实践和最终评估的组合，不照搬Python和框架使用路线。
- [LangChain Academy课程大纲](https://academy.langchain.com/courses/intro-to-langgraph)：参考状态/记忆、人工介入、流式交互与编排等能力覆盖；本课程主要学习自己实现机制。
- [Anthropic：Building effective agents](https://www.anthropic.com/research/building-effective-agents)：参考工作流与Agent的区分、简单实现起步与按需求增加复杂度；这是原则参考，不当作最新API说明。
- [Pi官方仓库](https://github.com/earendil-works/pi)：参考模型、运行内核与Coding应用的职责边界。官方当前仓库会变化，新教程开写前选定可复现版本；不混用不同版本的目录或包名，不据README推断未检查的具体实现。

上述资料已在本轮讨论中查阅，阶段顺序与范围是针对学习目标制定的课程建议，不声称是某份官方课程原大纲，也不声称逐模块照搬Pi。

## 11．这次审阅之后再做什么

本设计确认前，不删除旧教程/源码/GitHub仓库，不开始新版第1篇，不擅自更新现有技能和AGENTS来替换旧课程规则。

确认后先确定新版项目位置、旧项目保留方式、包与应用工作名，更新教学技能及项目约定以落实新设计，再细化第一阶段。学习者亲手实现框架与应用源码；作者负责教程、候选及临时验证，保留已有分工，除非另有明确安排。

新版建议使用独立的新本地目录和新Git仓库，后续连接独立GitHub仓库；旧项目与远程保留作历史参考，不在旧分支重置或覆盖。新课程从自己的第1篇开始，不要求完成旧19篇。仅迁入经确认的新版设计与必要规范，不复制旧src或整套章节作为新实现。仓库名、位置和GitHub可见性在创建前确定，不以“重来”推断删除或公开发布授权。

可以把确认后的课程设计与授权边界整理成新窗口提示词，让下一次对话先读设计、定位阶段、再继续；不依赖长聊天记忆维持主线。
