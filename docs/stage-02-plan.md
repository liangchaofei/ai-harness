### 第一阶段04的前置约束（学习源码已落实）

- Runtime首次请求模型时，由应用注入符合调用契约的函数；Runtime不直接导入DeepSeek适配实现，不在循环中判断提供商。
- 现有DeepSeek调用可以由应用传入，不先引入提供商注册系统或重写现有适配器。
- 调用契约根据04实际需要定义；第二阶段核对流式、取消等能力时允许有依据地演进，不承诺永不修改接口。

### 第二阶段实现范围

- [ ] 设计前读取固定版本Pi相应提供商接入链，核对两家服务第一方协议；第二家服务在本任务设计时确定。
- [ ] 在model包实现第二家提供商，分别处理鉴权、请求编码、响应解码与错误归类；不把协议转换放进Runtime。
- [ ] 收敛应用可选择的接入接口、模型配置与凭据归属；共用配置和提供商专属选项明确分开。
- [ ] 对齐文本、工具请求、工具结果反馈及停止原因；声明工具/流式等支持差异，不把不同服务假装成同一协议，不静默丢弃不支持的选项。
- [ ] 复用同一个Runtime、同一组工具和任务完成切换，保持请求ID关联及历史更新规则。
- [ ] 临时工程验证两家适配的正常、工具往返和失败路径；检查包公开入口、类型与构建产物。固定响应与真实服务证据分别记录，不自动调用付费服务，不读取或输出真实.env。

验收重点：换提供商只调整模型接入和应用配置，不修改Runtime核心、coding-tools或任务材料；不能只以新增适配文件、替换URL或类型检查通过作为完成。

### 责任边界

model负责服务差异和消息转换；Runtime负责调用、执行、状态和继续/停止；应用选择接入并提供凭据；coding-tools保持具体代码能力。适配任务与既有流式/取消专题协同，避免各自重复设计一套接口。
