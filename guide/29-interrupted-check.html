29 验收进程中断后，怎样核对现场 ​

第 28 篇通过移走回执模拟结果不明。这次让恢复 CLI 在验收子进程运行期间真的退出，再看两个进程分别留下了什么。

本篇在 Agent 的什么位置 ​

第五阶段「可靠执行与恢复」。这次观察的是恢复 CLI 调用本地验收之后、保存完成回执之前的窗口。

本篇技术方案 ​

实施前，先走完一次具体过程 ​

  1. 实验入口用固定模型改好路径处理函数，保存 pending.json，随后启动一个恢复 CLI。
  2. 恢复 CLI 按原逻辑校验副本、创建 .started，再启动验收子进程。子进程写下 .probe-started，等实验入口放行。
  3. 实验入口看到启动标记后，只结束自己启动的恢复 CLI，并等待该进程退出。随后写入 .probe-release。子进程继续执行原验收，把脚本的退出码写进 .probe-finished。
  4. 再次提交同一个检查点。操作者能看到子进程留下的通过线索，CLI 看到的仍只有占用标记，缺少由原恢复流程签发的完成回执，所以拒绝重跑。

实现架构图 ​

验收标准。 恢复 CLI 确实因信号退出，验收脚本随后记录 0，正式 .done 缺失，第二次恢复退出 2。本实验用固定模型控制交接位置。验证真实模型能否自主停在「改完且未验收」是另一项实验，本篇无需调用模型服务。

本篇核心代码在哪 ​

看 examples/interrupted-check/main.ts 的三处等待：先等 .probe-started，再等恢复 CLI 退出，最后放行子进程并等 .probe-finished。这个顺序让我们能确认验收在 CLI 退出之后完成。第 28 篇的 claimCheck 仍根据正式回执决定能否继续。

Pi 的 AgentSession.abort() 在发出取消后等待空闲，说明主动取消需要等运行退出。本篇用突然终止进程观察这条等待链无法完成时的磁盘状态。Pi 固定版本源码

第一步：让固定示例可以换一份任务配置 ​

打开 examples/checkpoint/main.ts。替换读取命令行参数的解构语句：

ts
const [mode, path, taskFile = 'fixtures/code-tasks/route.json'] = process.argv.slice(2);

替换传给 runCli 的第一个参数：

ts
  ['--task', taskFile, mode === 'save' ? '--checkpoint' : '--resume-check', path],

已有命令省略第三个参数时继续使用原配置。实验入口会把临时配置作为第三个参数传入，使恢复流程启动本篇的观察脚本。

改完的完整 examples/checkpoint/main.ts
ts
// 【新增文件】用固定模型在改完后交接，再用另一个进程恢复。
import { runCli } from '../../apps/coding-cli/src/main';

const [mode, path, taskFile = 'fixtures/code-tasks/route.json'] = process.argv.slice(2);
if (!path || (mode !== 'save' && mode !== 'resume')) {
  throw new Error('用法：main.ts save|resume <检查点> [任务配置]');
}

let turn = 0;
process.exitCode = await runCli(
  ['--task', taskFile, mode === 'save' ? '--checkpoint' : '--resume-check', path],
  () => {
    if (mode === 'resume') {
      throw new Error('恢复验收无需创建模型。');
    }
    return async () => {
      turn += 1;
      if (turn === 1) {
        return {
          role: 'assistant',
          content: '',
          stopReason: 'toolUse',
          toolCalls: [{
            id: 'edit_before_handoff',
            name: 'replace_text',
            arguments: JSON.stringify({
              path: 'src/routing/normalize.ts',
              oldText: "return path.split('?')[0]!.replace(/\\/$/, '');",
              newText: "const clean = path.split(/[?#]/)[0]!;\n  return clean.replace(/\\/+$/, '') || '/';",
            }),
          }],
        };
      }
      return {
        role: 'assistant',
        content: '已修改，等待验收。',
        stopReason: 'stop',
        toolCalls: [],
      };
    };
  },
);

第二步：让验收子进程留下独立线索 ​

新建 fixtures/code-tasks/check-route-interrupted.mjs，完整代码如下。它在运行原验收前等待实验入口放行。

完整 check-route-interrupted.mjs
mjs
// 【新增文件】给受控实验留下独立证据，再沿用原来的路径验收。
import { access, rename, writeFile } from 'node:fs/promises';
import { join } from 'node:path';
import { setTimeout } from 'node:timers/promises';

const workspace = process.argv[2];
await writeFile(join(workspace, '.probe-started'), '', { flag: 'wx' });
const release = join(workspace, '.probe-release');
for (let attempt = 0; ; attempt += 1) {
  try {
    await access(release);
    break;
  } catch (error) {
    if (error.code !== 'ENOENT' || attempt >= 250) throw error;
  }
  await setTimeout(20);
}
// CLI 退出后，原验收写 stdout 时可能遇到已关闭的管道。
process.stdout.on('error', (error) => {
  if (error.code !== 'EPIPE') throw error;
});
await import('./check-route.mjs');
const pending = join(workspace, '.probe-result-tmp');
await writeFile(pending, String(process.exitCode), { flag: 'wx' });
await rename(pending, join(workspace, '.probe-finished'));

在这个文件里，.probe-started 由验收子进程自己创建。因此看到它时，可以确认程序已经进入脚本。随后循环等待 .probe-release。放行后执行以下几行（摘录已包含在完整实现中）：

js
await import('./check-route.mjs');
const pending = join(workspace, '.probe-result-tmp');
await writeFile(pending, String(process.exitCode), { flag: 'wx' });
await rename(pending, join(workspace, '.probe-finished'));

CLI 退出时会关闭接收 stdout 的管道，原验收输出可能遇到 EPIPE。实验脚本只处理这个预期错误，让独立证据还能写出，其他输出错误照常抛出。原脚本根据根路径等用例设置 process.exitCode。这里先把值写进临时文件，等写完再改名为 .probe-finished，避免观察进程刚看到文件就读到空内容。正式回执还需要恢复 CLI 收到工具返回、重新核对副本并执行 saveCheckReceipt。

第三步：真的中断一次，再比较证据 ​

新建 examples/interrupted-check/main.ts。它生成临时任务配置，启动本地 CLI，最后核对信号、文件和退出码。

完整 examples/interrupted-check/main.ts
ts
// 【新增文件】只中断本脚本启动的恢复 CLI，并核对磁盘证据。
import assert from 'node:assert/strict';
import { spawn } from 'node:child_process';
import { access, mkdtemp, readFile, writeFile } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import { join, resolve } from 'node:path';
import { setTimeout } from 'node:timers/promises';

const dir = await mkdtemp(join(tmpdir(), 'ai-harness-interrupt-'));
const checkpoint = join(dir, 'pending.json');
const taskFile = join(dir, 'route.json');
const original = JSON.parse(await readFile('fixtures/code-tasks/route.json', 'utf8'));
await writeFile(taskFile, JSON.stringify({
  ...original,
  source: resolve('fixtures/route-repair'),
  checkScript: resolve('fixtures/code-tasks/check-route-interrupted.mjs'),
}));
console.log('实验目录', dir);

function start(mode: 'save' | 'resume') {
  const child = spawn(process.execPath, [
    '--import', 'tsx', 'examples/checkpoint/main.ts', mode, checkpoint, taskFile,
  ], { stdio: 'inherit' });
  const closed = new Promise<{ code: number | null; signal: NodeJS.Signals | null }>(
    (resolveClose, reject) => {
      child.once('error', reject);
      child.once('close', (code, signal) => resolveClose({ code, signal }));
    },
  );
  return { child, closed };
}

async function waitForFile(path: string): Promise<void> {
  const deadline = Date.now() + 5_000;
  while (Date.now() < deadline) {
    try {
      await access(path);
      return;
    } catch (error) {
      if ((error as NodeJS.ErrnoException).code !== 'ENOENT') throw error;
    }
    await setTimeout(20);
  }
  throw new Error(`等待证据文件超时：${path}`);
}

assert.equal((await start('save').closed).code, 0);
const { workspace } = JSON.parse(await readFile(checkpoint, 'utf8'));
const running = start('resume');

try {
  await waitForFile(join(workspace, '.probe-started'));
  assert.equal(running.child.kill('SIGKILL'), true);
  assert.equal((await running.closed).signal, 'SIGKILL');
  console.log('恢复 CLI 被中断，子进程已启动');
} finally {
  if (running.child.exitCode === null && running.child.signalCode === null) {
    running.child.kill('SIGKILL');
  }
  await running.closed;
}

await writeFile(join(workspace, '.probe-release'), '', { flag: 'wx' });
await waitForFile(join(workspace, '.probe-finished'));
const exitCodeText = await readFile(join(workspace, '.probe-finished'), 'utf8');
assert.equal(exitCodeText, '0');
await access(checkpoint + '.started');
await assert.rejects(access(checkpoint + '.done'), { code: 'ENOENT' });
console.log('验收脚本记录通过，但 CLI 没有完成回执');

assert.equal((await start('resume').closed).code, 2);
console.log('重新提交被拒绝，保留实验目录和工作副本供检查');

在该文件的第一个 try 内，下面几行决定中断发生在哪个边界（摘录）：

ts
  await waitForFile(join(workspace, '.probe-started'));
  assert.equal(running.child.kill('SIGKILL'), true);
  assert.equal((await running.closed).signal, 'SIGKILL');

running.child 指向实验入口创建的恢复 CLI，验收脚本是该 CLI 另行启动的子进程。kill 返回后还要等 closed，确认收到的退出信号。离开 finally 后才写 .probe-release，因此脚本通过时，已经没有原 CLI 来接收结果。最后用另一个恢复 CLI 提交同一个检查点，验证它停在第 28 篇的回执判断。

bash
npm run check
node --import tsx examples/interrupted-check/main.ts
看哪里本次实验的结果
恢复 CLI 的退出信号SIGKILL
旧副本里的 .probe-finished0，原验收脚本的通过线索
pending.json.started / pending.json.done占用存在，完成回执缺失
重新提交退出 2，保留现场

实验会打印临时目录和工作副本位置，便于回查。放行后的脚本有界运行，等待证据也有超时。本篇的观察限定于这组本地进程与脚本。若要把外部结果用于正式恢复，下一步需要定义可信的证据来源和人工处置规则。
